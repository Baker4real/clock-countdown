# 办公室设备部署

使用 `Deploy-OfficeCountdown.ps1` 部署到 Tailscale 中的办公室设备。脚本只允许从干净且已推送的 `main` 部署：先验证 Git 状态、生成 Windows 字节格式安装包并核对 canonical 发布契约中的 SHA-256；源码包同时包含部署控制器，解压预检会逐项核对所有声明源文件，远端再用整个 ZIP 的 SHA-256 覆盖这些源码。正式部署时再检查 Tailscale 连通性，直连或官方 DERP 中继均可，并通过受管 SSH helper 上传。远端短脚本只负责包哈希、解压、发布包复核和调用 `Countdown.RemoteDeployment.psm1`；该 module 统一拥有候选安装、稳定 validation 门禁、事务验收、回滚和提交后收尾。远端验收在全机安装事务锁内完成；安装器会原子写出独立的延期提交回执，即使 stdout 被截断或无法解析，部署端仍能定位并回滚候选事务。桌面路径按 Explorer 所属用户的 SID 注册表环境解析，不使用 SSH 身份的环境变量；远端与安装器会交叉核对用户、会话和桌面路径，变化时不创建事务，并在最终提交前再次核对。设置等价基线取自旧应用停止后的事务快照，因此远端测试与校时期间完成的用户保存会进入受保护基线，不会被更早的读数误判为部署篡改；最终设置读取、等价验证和事务提交持有应用保存使用的同一把跨进程写锁，关闭了读取到提交之间的竞态。事务直到哈希、设置等价、WPF 验证、计划任务和本次启动回执都通过才提交；提交动作还会再次核验桌面启动器仍等于事务记录的候选 SHA-256。任一步正常失败都会由同一事务恢复原安装目录、两个计划任务、桌面启动器（含 `.new` 暂存）、遗留 `.cmd` 启动器和 Windows 时间服务状态。损坏 journal 或缺失备份会停止在安全边界；候选期间若用户替换桌面文件，事务会恢复应用、任务和时间服务，保留用户文件与 journal 证据，并拒绝把部署误报为成功。

硬约束：发起端与办公室设备都必须运行 PowerShell 7+（`pwsh.exe`）。部署脚本和安装器会拒绝 Windows PowerShell 5.1，不提供 fallback。

办公室 SSH 会话通常没有交互桌面。远端 C# 回归关闭第二实例「激活失败」模态提示时，必须按该进程 PID 枚举全部顶层窗口（标题「敏敏子倒计时」）；窗口已创建但 `IsWindowVisible=false` 仍算提示出现。悬浮窗激活成功路径对空 Win32 可见枚举改用 WPF 计数，是同一约束。发布包不含源码树视觉基线时，办公室 C# 断言数会低于本机 SourceTree 套件，这是 ReleasePackage 模式，不是回归缺项。远端 Core 回归会现场自包含发布 FakeDotnet 夹具；办公室内存紧张时可能 OOM，失败回执会写在 Core 回归阶段并回滚，不要当成 SSH 或传输失败。安装期验证套件的窗口化子步骤（C# 回归、兼容 UI 回归、应用 validate-only）在办公室远端部署的延迟提交事务上下文（`-ParentTransactionMutexHeld`，只与安装器 `-DeferCommit` 同用）下，经子进程环境注入 `MINMIN_SUITE_ALLOW_UNISOLATED=1` 直接启动，不进自建隔离桌面：SSH 会话无法在该桌面初始化 GUI 子进程（退出码 -1073741502 / 0xC0000142），且该上下文窗口对交互用户不可见（`IsWindowVisible=false`），卸隔离不把测试窗口漏上用户屏幕。本地交互上下文不带该标记，隔离 fail-closed 语义不变；该双分支由 `Countdown.Core.Tests.ps1` 的验证接口契约测试钉住。

远端安装主体不得内嵌到 `ssh.exe` 的命令行。部署器会把长脚本以 UTF-8 无 BOM 写入本次 `run-evidence` 目录，计算 SHA-256 后经同一组严格 SCP 参数上传；办公室端先复核脚本哈希，再用短命令执行 `pwsh.exe -File remote-install.ps1`，并把非零退出码传回发起端。这既保留了脚本完整性，也避免触发 Windows 进程命令行长度上限。

若部署失败，原本已使用 `pwsh.exe` 的计划任务会恢复原状态；检测到遗留 `powershell.exe` 任务时，回滚会改为当前已验证的 PowerShell 7 路径，以保持该硬约束。Windows 时间服务的启动类型和运行状态会恢复；已经发生的网络校时不尝试倒退。

远端安装脚本失败时，部署端会以同一套严格 SSH 参数回读 `deployment-failure.json`。办公室端仅读取不超过 `32 KiB` 的非 reparse point 普通文件；发起端只接受有效 UTF-8、`24 KiB` 以内、字段白名单精确且 `commitState` 与回滚状态组合有效的 schema v2 回执。通过验证的字段会规范化后保存为本次 `run-evidence\remote-deployment-failure.json`；回执缺失保留原始部署失败，损坏或读取失败也会使部署失败闭锁。`commitState` 只能是 `committed`、`not-committed` 或 `unknown`；`unknown` 只表示无法确认提交边界，不能据此声称未提交或已经回滚。

未提交的候选部署失败时，远端控制器会在调用 rollback 前尽最大可能原子写入同一暂存目录下的 schema v1 `pre-rollback-diagnostics.json`。它记录候选 PID/会话/应用路径、startup/runtime/acceptance 三份协议文件的状态、`requested/released/ready/finalized` 时间与身份匹配、acceptance 原子写临时文件、候选进程、计划任务、错位回执和四份应用日志的有界结构化 tail；实际 launch token、settings 内容、任务 XML/arguments、SSH 参数和凭据不会写入。sidecar 使用 UTF-8 无 BOM且不得超过 `24 KiB`；采集失败不阻止或重试 rollback，原部署异常保持为主异常，并追加“rollback 前诊断捕获失败”摘要。

远端安装失败后，部署器无论失败回执读取结果如何，都会再以同一严格 SSH 和传输账本接口回读 sidecar。远端读取仍限定为不超过 `32 KiB` 的非 reparse point 普通文件；本地 parser 再拒绝 BOM、无效 UTF-8、超过 `24 KiB`、未知 schema、额外字段或无效类型，只把规范化结果保存到本次 `run-evidence\pre-rollback-diagnostics.json`。sidecar 缺失、损坏或读取失败会明确进入最终异常，但不会覆盖已取得的原始部署失败或 `remote-deployment-failure.json`。

正式部署源固定为已经推送且与 `origin/main` 一致的当前 `main` 提交。正式无开关路径使用 `git archive` 导出 `commit-source.zip`，解压到本次 evidence staging 后，再以提交中的 `commit:path` blob identity 和 `git hash-object --no-filters` 逐项核对部署控制文件，随后才导入发布契约并构建 Windows 发布包。仓库通过 `.gitattributes` 将受管文本固定为 LF；正式部署不得改用当前工作树副本、任意外部归档或绕过 blob identity / SHA-256 门禁的包。

部署默认保持既有 `settings.json` 字节不变。唯一允许的变化是 schema v3-v9 严格等价迁移到 canonical schema v10：v3-v6 只补齐既有迁移字段并保持提醒关闭；v7 的关闭、一次和循环提醒分别迁移为空规则、`absoluteOnce` 和 `fixedInterval`，循环首次到期仍等于旧起点加一个间隔；v8-v9 的 `none` / `once` / `repeat` 迁移为稳定 ID 的 v10 规则，并用有界 cursor 保证已送达一次提醒和已开始循环不会复活。v3-v8 只补 `themePreference: "Auto"`，v9 保留原主题偏好。迁移不得新增提醒、改变送达/处置/稍后状态、伪造历史便签日期或改变标签关联、记录顺序、UTC 时刻及其他领域值；合法空集合或记录删减也不得被旧快照回滚。迁移 rule ID 必须在重复读取和失败重试间稳定，任何其他变化都会使验收失败并触发回滚。

安装后应用 validate-only 必须显式使用事务目录内的唯一隔离 settings 文件，并在 `finally` 清理其伴生文件。验证前后会把现役安装 `settings.json` 的指纹状态分别记录为 `Absent` 或 `Present`：首次安装时稳定的 `Absent -> Absent` 是合法状态；`Present` 状态除长度、修改时间和 SHA-256 外，还必须保持 NTFS 卷序列号和文件索引不变。状态变化、文件对象被替换或任何内容污染都会失败闭锁。

部署前先做本地预检：

```powershell
pwsh.exe -NoLogo -NoProfile -File ./Deploy-OfficeCountdown.ps1 -ValidateOnly
```

正式部署：

```powershell
pwsh.exe -NoLogo -NoProfile -File ./Deploy-OfficeCountdown.ps1
```

上述命令的脚本路径统一用 `./` 前缀：该写法在 PowerShell、cmd 与 Git Bash 下均可直接执行；`.\` 会被 Git Bash 等 POSIX shell 当作转义符吃掉反斜杠，导致 `pwsh -File` 找不到脚本。

`-ValidateOnly` 是独立的本地候选门：它在任何 Git 或远端逻辑前读取当前工作树的 `Countdown.ReleaseContract.psm1`，验证 `PackageFiles` 精确清单及 `IntegrityHashes` 静态 SHA-256，再把这些当前字节写入唯一的 D 盘临时 ZIP，重开 ZIP 逐项复核 entry 清单和哈希，并在成功或失败时都删除该 ZIP。它不要求工作树干净，不运行 `git fetch`，也不会加载 SSH helper、连通办公室设备或执行远端命令。正式无开关路径仍会在构建前、构建后、打包前、打包后和远程输出前检查工作树、`main`、`HEAD` 与 `origin/main`，并只从通过 blob identity 校验的提交快照发布。`PackageFiles` 还包含不进 `IntegrityHashes` 的构建产物（当前为 `verification\MinminCountdown.Verification.exe`）；正式路径在 snapshot 构建后读取其 SHA-256 写入 packageManifest，远端按该本次构建哈希锁定。改了 `IntegrityHashes` 覆盖的文件后，必须先把契约哈希更新进已推送的 `main`，否则正式部署会在源文件锁定阶段失败。

因此本机 `-ValidateOnly` 通过只表示当前 working-tree candidate 的本地发布合同通过，不表示该候选已提交或推送，也不表示产物已经上传、安装、提交事务或经过办公室远端验收。正式完成态仍要求干净且已推送的 `main`、成功回执、传输账本、deployment binding 与独立运行态回读全部匹配。

正式部署不再依赖固定睡眠时间或旧的 PID 文件。安装器在启动前生成唯一令牌；悬浮窗首次完成渲染后写入带令牌、进程、交互会话、脚本路径和日历状态的 `window-ready` 回执。这个第一阶段不要求日历就绪，日历仍可处于 `Pending` 或 `Unavailable`，因此网络日历不可用不会冒充启动失败；节假日日历请求在首帧之后异步进行，不会阻塞悬浮窗显示。设置等价和提交前验收通过、事务进入仍可回滚的 `accepted` 后，安装器再发出最终解锁请求，并且必须收到同一令牌、进程、会话和应用路径的 `finalized-ready` 回执；计划任务、受管 EXE 身份与运行环境复核仍一致后，部署才把事务标记为 `committed` 并报告成功。

远端命令返回后，部署端只接受一个字段集合精确、类型和值域均符合 schema v1 的成功对象；缺失/额外/重复字段、截断 JSON、多对象或噪声输出都会失败闭锁。对象必须确认计划任务 `Ready` 且 `LastTaskResult=0`、`window-ready`、`finalized-ready` 和三组测试计数有效，并记录现役 `settings.json` 部署前后长度、mtime 与 SHA-256；规范化后以 UTF-8 无 BOM 原子保存为本次 `run-evidence\remote-deployment-success.json`，且不保存原始 launch token 或凭据。应用仍在跑由 `RuntimeProcessId` 与进程路径/EXE 哈希证明，不再用任务 `Running` 冒充进程存活。远端已经提交但本地成功回执无法解析或持久化时，脚本必须报告“已提交但本地证据不完整”，不得声称已回滚。

成功回执持久化后，部署器自动执行两次独立严格 SSH 回读。第一次读取并验证 `deployment-binding.json` 的 binding 哈希、token 哈希与成功回执 PID。第二次回读不再把回读脚本内嵌进远程命令行：部署器把 reader 脚本以 UTF-8 无 BOM 写入本次 `run-evidence`，计算 SHA-256 后经同一组严格 SCP 参数上传到按 runId 唯一的远端暂存目录下的固定文件名 `post-deployment-independent-readback.ps1`，传输账本将其独立记账为 `post-deployment-independent-readback-script`；随后只用一条长度固定、与脚本大小无关的短 ssh 命令在办公室端复核脚本是非 reparse point 普通文件且 SHA-256 匹配，再以 `pwsh.exe -File` 执行并回读结果，哈希不匹配会在执行前中止。第二次回读重新读取办公室主机/用户、计划任务执行文件/参数/工作目录、`startup-request.json`、`runtime-status.json`、`acceptance-status.json`、真实进程和当前 settings。只有登录任务为 `Ready` 且 `LastTaskResult=0`，三份协议分别达到 `finalized`、`window-ready`、`finalized-ready`，token 哈希、PID、会话、应用/进程路径、运行 EXE 发布哈希和成功回执 settings 的 SHA-256/长度/mtime 全部匹配，才会原子保存 `deployment-binding.json` 与 `post-deployment-independent-readback.json`。`SettingsUnchanged=true` 表示部署前后长度、mtime 与 SHA-256 均相同；允许的 schema 迁移会记为 `false` 并保留前后指纹。回读只保存身份和 token 的 SHA-256 或匹配结果，不保存原值；ISO 时间戳保持 JSON string，数组、嵌套对象、浮点数、重复字段或其他 token 漂移一律拒绝。此时部署已提交，任何回读或证据写入失败都报告“已提交但独立验证不完整，未回滚”。

脚本会将本次包、哈希和传输证据保存到 `D:\agents\run-evidence\clock-countdown-deploy\`。它不复制、打印或提交 SSH 密钥和办公室设备凭据；连接配置仅由本机受管 helper 提供。

正式部署在受管 helper、destination 形态校验和 Tailscale 连通检查之后、首次传输之前，解析本次使用的 ssh/scp 绝对路径。候选优先级为：Windows 内置 OpenSSH 标准目录 `$env:SystemRoot\System32\OpenSSH\` 中成对的 `ssh.exe`/`scp.exe` 优先；否则用 `Get-Command -CommandType Application` 的 PATH 解析兜底，且 ssh 与 scp 必须位于同一目录。找不到任何成对候选即闭锁。部署脚本的全部 SSH/SCP 进程启动都使用这些绝对路径，并显式传入传输账本的可选可执行路径参数；不维护“已知坏实现”黑名单。

随后用选定的 `ssh.exe` 向办公室设备发送一条只读 echo 行为探针：远程命令约 32KB，覆盖历史独立回读 22644 字符命令量级并留余量，作为对回读通道固定短命令的纵深防御。尺寸发现只证明本机 `ProcessStartInfo`/`ArgumentList` 能通过 CreateProcess 长度门，使用等长 dummy destination/文件名，不对办公室 destination 启动 ssh；正式 `$officeDestination` 只出现在最终那一次 echo。若 32KB 无法启动，则改用仍能启动且不小于 22644 的最大尺寸，并把实际探针字符数写入错误和本次 `run-evidence\ssh-client-identity.json`。禁止静默缩到 22644 以下。完整往返（输出含结尾标记且长度与期望一致）才放行；截断、启动失败或远端错误即闭锁，错误消息包含解析到的二进制路径、版本和实测截断长度。探针只读，不改变远端状态。解析到的二进制路径与版本只写入本次 run-evidence sidecar，不进入 `transfer-attempts.json`，也不记录 SSH 参数或凭据。

部署 ZIP、`remote-install.ps1` 与部署后独立回读脚本 `post-deployment-independent-readback.ps1` 三次 SCP，以及成功后的 `remote-deployment-binding`、`post-deployment-independent-readback` 两次 SSH 回读，都通过 `Countdown.TransferLedger.psm1` 的同一个 interface 执行；回读脚本上传独立记账，SSH 回读条目的耗时不含脚本上传耗时（上传由 scp 条目独立计时）。每次命令返回后立即原子更新本次 `run-evidence\transfer-attempts.json`，记录 method、状态、退出码、bytes、完整命令墙钟耗时、MiB/s 和 Mbps；Stopwatch 从启动外部命令前开始，到进程退出后停止，因此包含 SSH 握手。成功 bytes 对 SCP 固定为本地源文件长度，对 SSH 回读固定为实际 payload 长度。

非零 SCP 退出时，部署器用同一组严格 SSH 参数尽最大可能回读远端部分文件长度：有正字节记录为 `failed`，确认远端为零字节才记录为 `failed-before-transfer`；probe 本身失败则记录 `failed-bytes-unverified`、`transferStarted=null`、`bytesVerified=false`，保留零值数值字段但不冒充“未传输”。SSH 回读命令失败同样记录 `failed-bytes-unverified`；若已取得 payload 但 schema 或交叉绑定失败，则记录实际 bytes 和吞吐后让部署失败。远端安装失败后的 `remote-deployment-failure-receipt` 与 `pre-rollback-diagnostics` 也使用同一账本。账本不记录命令行、私钥、known-hosts 或其他 SSH 参数；远端 NTFS 文件时间戳只能作为事后写入窗口，不能替代该账本。
