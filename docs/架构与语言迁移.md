# 架构与语言迁移

## 决策

项目采用混合架构：

- C# / .NET 10 WPF 负责应用宿主、界面、领域行为和设置持久化。
- PowerShell 7 继续负责薄启动 adapter、计划任务、安装事务和办公室部署。
- `敏敏子倒计时.ps1` 只负责把既有命令行参数传给 `app\MinminCountdown.exe`，生产启动时强制要求有效启动请求，等待进程退出并传播退出码；EXE 或请求缺失时明确失败，不回退到旧 PowerShell WPF 宿主。

迁移采用渐进式切换，但当前生产宿主已经完成迁移：办公室计划任务通过 PowerShell 薄 adapter 启动受管 C# EXE，旧 PowerShell WPF 宿主只保留为兼容回归基线。这不是整仓换语言。原有 PowerShell 安装与部署 module 已具有事务、回滚和 Windows 运维能力，重写它们只会增加迁移风险；原应用宿主则长期集中窗口生命周期、动态状态、渲染和事件处理，迁入 C# 可以获得更强的类型检查、IDE 支持和 WPF 工具链。

## Module 与 seam

### C# 应用宿主

`src\MinminCountdown` 是桌面应用 module，发布为 self-contained 的 `app\MinminCountdown.exe`。它的外部 interface 是命令行参数、`settings.json` 和 `runtime-status.json`；调用者无需了解内部窗口、计时器、筛选或提醒实现。

### C# 设置核心

`src\MinminCountdown.Core` 把 schema 迁移、规范化校验、原子写入和跨进程写锁收拢在一个 module 中。应用宿主和验证程序都通过同一 interface 读写设置，形成一个可直接测试的真实 seam。

### PowerShell 启动 adapter

`敏敏子倒计时.ps1` 保留既有计划任务和部署 interface，只做参数映射与进程退出码传播。删除它会迫使安装器、计划任务和部署器同时理解 EXE 参数，因此这个小 module 仍提供兼容 leverage。

### PowerShell 运维 adapter

`Countdown.InstallTransaction.psm1`、`Countdown.Runtime.psm1`、`Install-Countdown.ps1` 和 `Deploy-OfficeCountdown.ps1` 继续负责 Windows 主机 seam：计划任务、交互会话、时间服务、事务快照、回滚、启动就绪和远端传输。这些行为不进入桌面应用实现。

## 不丢数据契约

- 可读取 schema v1-v7，只写 canonical schema v7。
- schema v6 到 v7 只新增关闭状态的提醒字段；更早版本按既有规则补齐字段，不伪造历史便签日期。
- 规范时区固定为 `China Standard Time`。
- 写入使用 UTF-8 无 BOM、同目录临时文件、原子替换和按设置路径命名的跨进程 mutex。
- 候选状态持久化成功后才提交到界面；失败时保留旧文件、内存状态和编辑草稿。
- `-ValidateOnly` 对传入设置保持只读。
- 安装事务对所有 D 盘操作路径逐级拒绝 junction、符号链接等 reparse point，并在递归复制、恢复或删除前重新扫描目录树，避免词法子路径越界到事务根之外。
- 安装事务启动候选应用时写入带同一 token 的 `active`“验收只读”请求；`released` 只授权 C# 写入必要的 schema 迁移，C# 写入成功后回报 `ready`，此时窗口仍不可编辑。事务先进入仍可回滚的 `accepted` 并保留备份；写入 `finalized` 后，同一 C# PID 在一个 Dispatcher 回调内启用窗口并原子写出 `finalized-ready` 回执，回执失败会立即重新禁用窗口。安装器持有设置写锁复验回执、会话、进程和任务后才把事务标为 `committed` 并清理证据；此前任一失败都停止候选并回滚。请求 schema 未知、文件缺失、损坏、不可读或 token 变化均保持只读或终止生产启动，失败回滚期间不存在会被旧快照覆盖的新用户保存。
- `committed` 清理在事务目录外先写 sidecar，再将事务目录同卷原子重命名后删除；即使部分删除已移除内部 journal 或目录重命名失败，后续 recovery 仍能定位并重试，持续失败才报告 unresolved，且 committed 永不重新进入回滚。
- 办公室部署以旧应用停止后的事务快照为基线，在同一设置写锁内比较迁移前后语义并提交事务；任何非允许变化都回滚。

## 启动与发布契约

- `runtime-status.json` 保持 schema v4。
- 回执中的稳定应用身份仍是 `敏敏子倒计时.ps1`，PID 必须对应 `app\MinminCountdown.exe`。
- “启动就绪”仍表示悬浮窗首次完成渲染；节假日日历可以是 `Pending`、`Ready` 或 `Unavailable`。
- 计划任务使用 `pwsh.exe -STA` 启动薄 adapter；这是现役兼容 seam，不表示 C# 应用宿主迁移尚未完成。
- 生产启动回执默认只接受受安装器管理的 C# EXE；旧 PowerShell WPF 宿主仅能在显式兼容回归中启用。
- 安装与办公室部署在提交前重新读取同一 token 的回执，并确认 PID、会话、应用路径和 `Running` 任务均未变化。
- 发布使用 self-contained、single-file、`win-x64`，目标机不需要预装 .NET 10。
- 办公室部署只接受干净且与 `origin/main` 相同的 `main`，随后从该提交 clean rebuild C# 产物，再读取清单并打包，避免复用陈旧的忽略目录二进制。
- 安装器完整性清单同时校验 C# 应用、验证器、C# 回归脚本、远端测试所需构建脚本和两套发布资产，共 34 项；构建脚本只随部署验证包传输，不复制到最终应用目录。

## 构建与验证

```powershell
pwsh.exe -NoLogo -NoProfile -File .\Build-CountdownApplication.ps1 -Clean
.\verification\MinminCountdown.Verification.exe
pwsh.exe -NoLogo -NoProfile -STA -File .\Countdown.CSharp.Tests.ps1
pwsh.exe -NoLogo -NoProfile -STA -File .\Countdown.Ui.Tests.ps1
pwsh.exe -NoLogo -NoProfile -File .\Countdown.Core.Tests.ps1
pwsh.exe -NoLogo -NoProfile -File .\Install-Countdown.ps1 -ValidateOnly
```

`Countdown.CSharp.Tests.ps1` 覆盖 PowerShell/C# 双向设置兼容、双向 mutex、真实 adapter UI 验证、schema v4 启动回执、EXE PID、真实第二实例和验收只读生命周期。旧 `Countdown.Ui.Tests.ps1` 作为迁移后的兼容基线保留，但生产入口不允许回退到旧 PowerShell WPF。

## 候选语言比较

| 方案 | 优点 | 缺点 | 本项目结论 |
| --- | --- | --- | --- |
| C# / .NET WPF | 原生匹配现有 WPF 与 Windows API；静态类型、调试、异步和测试工具成熟；可 self-contained 发布 | 仍是 Windows 专用；需要跟随 .NET LTS 升级并重新发布安全补丁 | 最适合应用宿主 |
| 继续全量 PowerShell | Windows 运维和部署脚本直接；现有知识与模块可复用 | 大型有状态 WPF 宿主的类型、事件和重构反馈弱；维护成本随 UI 复杂度快速上升 | 只保留运维 adapter |
| Python + Qt | 跨平台，业务代码表达简洁，库丰富 | UI 框架和打包模型整体更换；Windows 原生集成、启动体积与签名发布没有迁移收益 | 不推荐 |
| TypeScript + Electron | Web UI 生态成熟，跨平台，界面开发快 | Chromium 体积和更新面大；需重写 WPF 与 Windows 集成；内存占用更高 | 不推荐 |
| Rust | 内存安全、原生性能和单文件部署出色 | Windows 桌面 UI 生态与 WPF 迁移成本高；开发速度和维护门槛不匹配 | 不推荐 |
| C++ | Windows 原生能力和性能上限最高 | 内存安全、构建、依赖和 UI 开发成本显著增加；本项目没有性能压力证明其必要性 | 不推荐 |
| Go | 部署简单、并发和工具链稳定 | 原生桌面 UI 生态弱，WPF 行为需要重做；对当前应用没有明显 leverage | 不推荐 |

## 生命周期

.NET 10 LTS 支持结束不等于应用或 C# 失效。项目需要在支持期内升级到后续受支持的 .NET 版本、重新运行回归并发布新的 self-contained EXE。self-contained 只消除目标机预装运行时的要求，不会自动获得运行时安全更新。
