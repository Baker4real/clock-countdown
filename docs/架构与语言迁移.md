# 架构与语言迁移

## 决策

项目采用混合架构：

- C# / .NET 10 WPF 负责应用宿主、界面、领域行为和设置持久化。
- PowerShell 7 继续负责薄启动 adapter、计划任务、安装事务和办公室部署。
- `敏敏子倒计时.ps1` 只负责把既有命令行参数传给 `app\MinminCountdown.exe`，生产启动时强制要求有效启动请求；用 `Win32_Process.Create` 让 C# 进程离开计划任务作业，确认仍存活后 adapter 退出 0，登录任务回到 `Ready` 且 `lastTaskResult=0`。`-ValidateOnly`、exercise 与 `-ExitAfterReadyForTest` 仍等待进程退出并传播退出码。EXE 或请求缺失时明确失败，不回退到旧 PowerShell WPF 宿主。

按 [#189：WPF 渐进式 UI 精致化与现代化](https://github.com/Baker4real/clock-countdown/issues/189) 继续采用 WPF 渐进升级。办公室计划任务通过 PowerShell 薄 adapter 启动受管 C# EXE，旧 PowerShell WPF 宿主只保留在仓库中作为兼容回归夹具，不再安装到运行目录。这不是整仓换语言。原有 PowerShell 安装与部署 module 已具有事务、回滚和 Windows 运维能力，重写它们只会增加迁移风险；原应用宿主则长期集中窗口生命周期、动态状态、渲染和事件处理，迁入 C# 可以获得更强的类型检查、IDE 支持和 WPF 工具链。

Tauri + React + Rust 降为后置闸门候选：只有 WPF 批次完成后，才允许用隔离的 `520 x 390` 切片比较第一眼识别、交互、性能、无障碍、WebView2 离线部署和回滚成本。闸门切片不得取得真实设置写入权，也不改变现行生产入口。旧候选比较把 Rust 标为“不推荐”，其含义是“不作为当前全量重写的默认路线”；与保留一个可回滚的实验切片并不矛盾。

#209 闸门已于 2026-10-09 真实执行：Tauri/WebView2 切片在隔离桌面通过四场景捕获与四项关键交互（套件 run `20261009T134140436-800ddbc3`，回执 `status=passed`）。决定为**停止全面重写；部分采用**——视觉细节 parity、离线 WebView2 安装、打包签名回滚与 Core 复用证据均未建立，WPF 渐进升级保持唯一生产路径。证据与缺口清单见 `docs/evidence/clock-countdown-issue-209-tauri-candidate/README.md`。

## Module 与 seam

### C# 应用宿主

`src\MinminCountdown` 是桌面应用 module，发布为 self-contained 的 `app\MinminCountdown.exe`。它的外部 interface 是命令行参数和 `settings.json`；受管生产启动还通过 `startup-request.json` 输入验收请求，并以 `runtime-status.json` 和 `acceptance-status.json` 输出两阶段就绪回执。调用者无需了解内部窗口、计时器、筛选或提醒实现。

应用宿主内部继续按更深的 module 划分，避免窗口和启动生命周期直接承载领域规则：

- `DesktopWorkspace` 是倒计时、便签、标签和筛选的桌面工作区 module，位于不依赖 WPF 的 `MinminCountdown.Core`。调用方只读不可变 `Snapshot`、以 `Apply` 提交变更、以 `ApplyFilter` 换一个不可变筛选值、处置提醒；候选提交事务、规则提醒状态与重复提醒 cursor 都是它的 implementation（原 `ApplicationSession` 已并入，`DesktopWorkspace.Transactions.cs`）。删除与完成的短时撤销（#214/#233/#235）也在这里：`ApplyWithUndo` 在提交时捕获载荷并替换唯一最近操作槽，`Undo` 只恢复发起表面的载荷，10 秒时限按注入时钟计算，`SetUndoHovered` / `SetUndoFocused` 按表面暂停；`App` 的 250ms 节拍调用 `ExpireUndoIfDue`，窗口只订阅 `UndoChanged` 呈现或收起入口。`MainWindow` 与 `FloatingWindow` 只保留 WPF 渲染和控件事件，共用同一个工作区实例，两个窗口不再各自理解同一套状态规则。快照冻结、筛选值规范化、落盘失败保留、观察者异常、提醒事务与撤销槽的计时、替换和失败语义由 `MinminCountdown.Verification` 进程内 runner 直接经这个 interface 验证，不开窗口。
- `FloatingCountdownProjection` 是悬浮窗倒计时页的投影 module，同在 `MinminCountdown.Core`。它按一份工作区快照、当前时刻和工作日历给出的两条事实（今天的下班时刻、是否进入下班收尾）一次算出：哪些行出现、谁是唯一视觉主项、用户倒计时数量与剩余时间、空态文案与「清除筛选」，以及 #212 渲染签名条目。距离下班是带自己 `Kind` 的投影行，不再借用倒计时记录和保留 ID；`FloatingWindow` 只把行画成 WPF 元素，并按行 `Key` 维护行实例；秒位按 #239 直接切换，不再保留淡入簿记。两种“筛选激活”口径是现行行为，集中在这里：任意筛选约束（含只作用于便签的搜索、状态和日期条件）都让距离下班与下班收尾退出，倒计时空态文案和「清除筛选」只看标签、无标签和倒计时状态。这些规则由进程内 runner 直接经投影 interface 验证。
- `ReminderEditing` 与 `ReminderRulesEditorViewModel` / `ReminderRulesEditorWindow` 是提醒草稿的具体 module。ViewModel 持有隔离候选、表单字段、验证错误和新增/编辑/复制/删除/接受/取消命令，窗口只构建 WPF 视觉树并通过绑定处理焦点和渲染探针。绝对一次、固定间隔、类型化日/周/月/年 calendar 和 0 至 5,256,000 分钟的倒计时相对规则走同一校验；便签不暴露相对分支，倒计时最终提交还会用实时目标和 clock 重验派生时刻。calendar 只暴露频率、1 至 999 间隔、北京时间开始日期/时刻与周、月、年的类型化 selector，不接受自由 RFC 5545、例外日期、次数或截止条件。原位编辑保留 rule ID，新建或复制生成新 ID。
- `ReminderDeliveryCoordinator` 是到期发生项、真实渲染、送达重试和逐项处置的应用级生命周期 module。它以 `ReminderSource(kind, id)` 统一调度用户倒计时和便签，在进程内只维护一个 `ReminderCenterWindow`；未确认的相对 occurrence 随目标变化失效，已确认送达的历史 occurrence 保留到处置。窗口只负责稳定排序、滚动展示、主题与可访问交互；两类来源共用知道了、稍后和打开来源，完成动作只存在于便签。删除规则或来源后，协调器在同一 tick 清除对应条目和重试。所有持久化失败均保留条目并按 5、10、20、30 秒退避重试；送达失败期间禁用处置但保留打开来源。
- `FloatingTrayController` 统一负责悬浮窗与托盘入口的生命周期切换，生产宿主和验证入口共用这一控制器；`TrayIconHost` 只封装系统托盘 `NotifyIcon`、恢复菜单和退出命令。缩入托盘时先显示托盘入口再隐藏窗口，恢复时先显示并激活窗口再隐藏托盘入口，确保切换失败时始终保留可恢复路径。
- `InstanceActivationServer` / `InstanceActivationClient` 是普通交互进程的单实例激活 module。宿主在设置读取、恢复判断、迁移和窗口构造前先取得按用户、应用根和设置路径作用域化的 mutex 租约，并立即建立同 scope、仅当前用户可连接的命名管道实例；第二实例只进行一次 3 秒内的版本化请求。ACK 必须匹配协议版本、scope identity、request identity 和 `activated` 结果，否则按超时、协议错误、监听失败或拒绝非零退出。主处理器只调度到 Dispatcher 并调用 `FloatingTrayController` 的恢复/激活 interface，不持有 `DesktopWorkspace` 或管理窗口编辑 interface，因此不会改变筛选、草稿或设置。验收只读模式在 finalized 前不监听也不发送交互激活；`--validate-only` 与 exercise 在租约前分流。
- 主题资源层自 2026-09-10 起为单一日间主题：`ThemePreferenceResolver` 与 `Auto`/`Day`/`Night` 解析、夜间画刷和主题切换入口已随夜间主题退役删除，`ApplicationTheme` 只保留一组日间画刷并无参 `Apply()`。色值与系统对比度角色只在 `ApplicationTheme.Tokens` 配色表声明，启动入口先写入日间色板，`Apply` 再按对比度开关生成原色、冻结画刷与组件别名，App.xaml 不写色值；主窗口、悬浮窗与确认框在构造时登记 `PaletteChanged`，主题 module 不枚举具体窗口；旧设置 `themePreference` 值一律按日间解释（字段兼容保留，不回写强制修改）。`520 x 390` 悬浮窗与主窗口的现役视觉、布局与命中测试合同由 [DESIGN.md](../DESIGN.md) 的「暖粉日间」契约定义；界面仍由真实 WPF 控件渲染，raster 只承担装饰层，不构成旧版回退。
- `StartupAcceptanceProtocol` 是启动验收 protocol module。它集中读取 `startup-request.json`、写入 `runtime-status.json` / `acceptance-status.json`、推进 `active -> released -> ready -> finalized-ready` 状态；`App` 只调用该 interface，不直接散落 token、路径和回执写入规则。
- `startup-request.json` 必须提供可严格解析为 UTC 的 `requestedAtUtc`。同一时刻同时驱动 C# 初始设置迁移和 PowerShell 两次设置等价验收，避免验收期间跨越时间边界时得到不同迁移结果；普通交互运行期仍使用实时系统时钟，不冻结业务时间。
- `HolidayCalendar` 是工作日历 module。调用方只提交 UTC 时刻；module 内部选择北京时间年份、拒绝错年或重复日期缓存、合并同年刷新，并在跨年时取消旧刷新。只有 map 年份与当前北京时间年份一致时，才对外提供今天的下班时刻（`GetWorkdayEndUtc`）、下班收尾判断和“今日已赚”；source/cache adapter 按本地 `holiday-cache`、有效 HTTP 结果、随包 `holiday-data` 的顺序取值，联网结果覆盖随包冲突并写回本地缓存，缺少年份覆盖时保持未就绪。
- `ApplicationValidation` 统一拥有 `--validate-only` 的临时工作区、主题、工作日历、真实 WPF 窗口、托盘控制器、兼容 report 和资源释放；`App` 只选择验证模式并输出结果。主窗口与悬浮窗分别只通过一个 `RunValidationScenarios` interface 提供窗口内场景，细粒度探针留在各自 private implementation。需要控件名、模板部件或窗口字段的新探针写进窗口的场景 partial，只把 typed 结果交给报告（静态结构事实已按此迁入 `MainStructureScenarios` / `FloatingStructureScenarios`）；`ValidationReport` 与 `ValidationExercises`（各按区域拆成 `<类名>.<区域>.cs` 的 partial 文件）里按字符串名取控件的存量由 Tooling `validation:control-name-lookups` 按类合计钉成只减不增，按区域继续迁移。
- `--validate-only` 继续返回顶层字段唯一、可重复序列化的兼容 JSON 对象；具体字段数随新增验证面增长，不作为稳定架构合同。必须为真的行为字段在 `ValidationReport` 里各声明一次为验证事实（`Must(值, 含义)`），报告仍输出同名 bool；`Seal` 校验每条事实为 bool 且为真后才追加 `Valid`，任一失败时连同中文含义列出全部失败字段并拒绝输出。唯一例外是参考基线延后：窗口套件经 `MINMIN_COUNTDOWN_REFERENCE_BASELINE_DEFERRAL_LOG` 交给应用一份预先建好的记录时，`CrossInterfaceReferenceBaselinesCurrent` 失败与过期的参考 manifest（manifest 在、实拍已写出、比对未过）记进报告字段 `DeferredReferenceBaselineFailures` 和该记录，报告照常输出，套件跑完其余断言后以 75 退出；缺 manifest、没有实拍或其他事实失败照旧拒绝，安装验证与基线生成不带此变量，始终严格。PowerShell 侧不再逐字段重复断言这些事实，也不钉字段数或 `name:type` 形状，只读 `Valid`、契约字段，以及事实之外的度量、清单和随输入变化的字段。`ReminderEditingInterfaceBehavior`、`CalendarReminderBehavior`、`StartupAcceptanceProtocolInterfaceBehavior`、`HolidayCalendarInterfaceBehavior` 和 `ValidationReportContractBehavior` 五个现役字段均由生产 module 的真实临时文件、模拟时钟、状态推进、失败路径和派生结果 exercise 得出；字段名中的 interface 指行为契约，不要求对应可替换的 C# interface。`StartupAcceptanceProtocolModuleDeep` 与 `WorkdayCalendarModuleDeep` 两个旧字段只作为兼容别名保留，并映射到相应行为结果，不再通过固定布尔值、类型清单或固定 module 数量自证架构。桌面工作区移入 Core 后，原 `DesktopWorkspaceInterfaceBehavior`、`DesktopWorkspaceModuleDeep` 与 `CountdownReminderTransactionBehavior` 退出报告，同一批断言改由进程内 runner 承担。

### C# 设置核心

`src\MinminCountdown.Core` 把 schema 迁移、规范化校验、两代合法备份、确认恢复、原子写入和跨进程写锁收拢在一个 module 中。`SettingsStore` 通过窄的 `ISettingsFileOperations` 系统边界执行可故障注入的同目录写入：backup 1 先以 rollback 保护方式轮转为 backup 2，随后一次 `File.Replace` 同时提交主文件并捕获旧主为 backup 1；任何旧主必须先通过严格合同，恢复也必须从主路径回读成功。`DesktopWorkspace` 只接收已经完成恢复门的设置，`App` 在创建窗口前提供“恢复备份 / 退出”决策，因此不会把未持久化候选或未经回读的恢复状态提交给交互宿主。

schema v10 在倒计时和便签上统一持有 0 至 8 条稳定 ID 的判别式提醒规则；倒计时可额外保存只含 offset 的 `countdownRelative`，派生 UTC 始终由当前目标实时计算。calendar recurrence 由固定 `Ical.Net 5.2.3` 计算，项目只负责把受限类型化 selector 映射为库规则、按 `China Standard Time` 转换 occurrence、再校验 selector 边界；不存在日期由库语义跳过，应用不手写另一套重复引擎。顶层按 rule ID 保存有界 cursor、最后送达 occurrence、最后处置 occurrence 和可空的活动稍后覆盖；处置必须建立在真实送达上且不晚于最后送达，活动稍后必须绑定同一未处置 occurrence。应用宿主、验证程序和 PowerShell oracle 都通过同一 canonical JSON interface 读写，形成一个可直接测试的真实 seam。

WPF 宿主以 `ReminderRulesEditorWindow` 作为主窗口倒计时、主窗口便签和悬浮快速便签共用的规则编辑 seam。`ReminderRulesEditorViewModel` 只操作隔离草稿并复用 `ReminderEditing` 校验；窗口通过绑定呈现候选和错误，调用方仅在对话框接受后替换自己的候选规则集合，最终仍由 `DesktopWorkspace` 以整条来源事务提交。`520 x 390` 悬浮倒计时表面不新增规则控件，继续由现有“管理”入口进入主窗口。

### PowerShell 启动 adapter

`敏敏子倒计时.ps1` 保留既有计划任务和部署 interface，只做参数映射。生产启动把 C# 进程移出计划任务作业后退出 0；validate/exercise 仍传播退出码。删除它会迫使安装器、计划任务和部署器同时理解 EXE 参数，因此这个小 module 仍提供兼容 leverage。

### PowerShell 运维 adapter

`Countdown.InstallTransaction.psm1`、`Countdown.InstallLifecycle.psm1`、`Countdown.Runtime.psm1`、`Countdown.Validation.psm1`、`Countdown.RemoteDeployment.psm1`、`Countdown.TransferLedger.psm1`、`Install-Countdown.ps1` 和 `Deploy-OfficeCountdown.ps1` 继续负责 Windows 主机 seam：计划任务、交互会话、时间服务、验证、事务快照、回滚、启动就绪和远端传输。`Countdown.Validation.psm1` 通过版本化 interface 运行并解析 Core、C#、兼容 UI 和应用 validate-only；旧四段 JSON 只作为兼容字段保留。`Countdown.RemoteDeployment.psm1` 通过生产 Windows adapter 和测试 adapter 统一候选安装、验证门禁、事务验收、失败回滚、资源释放，以及成功/失败回执、部署 binding、独立运行态回读和回滚前诊断的严格 schema。`Countdown.TransferLedger.psm1` 统一记录三次 SCP（部署包、`remote-install.ps1` 与部署后独立回读脚本，后者经短 SSH 命令复核哈希后以 `pwsh -File` 执行）、成功后的 binding 与独立回读，以及失败回执与回滚前诊断回读的命令耗时、字节数、吞吐和失败状态。`Deploy-OfficeCountdown.ps1` 只保留打包、SSH/SCP adapter 与远端 module 启动；远端提交后，它先严格解析并原子保存 `remote-deployment-success.json`，再以独立 SSH 读取 binding，交叉验证主机、用户、任务、三份协议回执、token 哈希、PID、会话、应用路径、EXE 和 settings，并保存 `post-deployment-independent-readback.json`。提交后的回读或本地证据写入失败只报告“已提交但验证不完整”，不得触发或声称回滚。`Countdown.InstallLifecycle.psm1` 是本机安装器与办公室部署 adapter 共用的安装事务生命周期：装入候选、事务验收（设置等价、环境与进程身份复验、`finalized-ready` 确认和提交后清理）与回滚都在其内，计划任务、时间服务、进程与桌面图标经 port 注入；安装布局只由 `Get-CountdownInstallLayout` 定义。这些行为不进入桌面应用实现。

## 不丢数据契约

- 可读取 schema v1-v10，只写 canonical schema v10；v1-v8 的主题偏好默认迁移为 `Auto`，v9 保留已有主题偏好。
- schema v7 的循环提醒无损迁移为 `fixedInterval`，首次到期时间等于旧起点加一个间隔；v8-v9 的 `none/once/repeat` 确定迁移为空规则、`absoluteOnce` 或 `fixedInterval`，delivered once 和已开始 repeat 通过有界 cursor 保持升级后不复活历史 occurrence。更早版本按既有规则补齐字段，不伪造历史便签日期或开启提醒。
- 迁移 rule ID 由来源类型、记录 ID 和旧提醒分支稳定派生；occurrence key 由 rule ID 与规范 UTC 计划时刻组成。重复读取、迁移重试和 canonical 往返不得改变二者。
- 主窗口倒计时、主窗口便签和悬浮快速便签共用现役 v10 多规则编辑器，支持新增、原位编辑、复制与删除；原位编辑保留 rule ID，新建或复制生成新 ID。旧单规则入口只作为兼容 adapter 保留，不是现役 UI。
- `lastDeliveredOccurrenceKey` 与 `lastDispositionOccurrenceKey` 分别表达真实渲染送达和用户成功完成处置；处置 key 必须属于同一规则、位于 cursor 内、具有送达事实且不晚于最后送达。`activeSnooze` 只保存当前未处置 occurrence 的 key、原计划 UTC 与覆盖 UTC，不改写基础规则；读取器兼容此前 provisional `lastAcknowledgedOccurrenceKey`，规范写出只使用 disposition 字段并显式写出可空 snooze。
- 规范时区固定为 `China Standard Time`。
- 写入使用 UTF-8 无 BOM、同目录临时文件、原子替换和按设置路径命名的跨进程 mutex。
- 合法保存维护 `settings.json.backup1` / `.backup2` 两代设备本地历史；无效主不晋升，轮转或替换失败不提交主文件与应用候选，并回滚已发生的 backup 2 轮转。
- 缺失主文件按首次运行处理；合法主永远优先。只有损坏或不可读主才允许显式恢复，且批准、原始字节证据、原子替换和主路径回读必须依次成功后才能创建交互宿主。
- 备份与 `settings-recovery-evidence` 不属于发布、诊断或跨设备同步接口；部署不得覆盖目标设备的这些状态。
- 候选状态持久化成功后才提交到界面；失败时保留旧文件、内存状态和编辑草稿。
- `-ValidateOnly` 对传入设置保持只读。
- 安装事务对所有 D 盘操作路径逐级拒绝 junction、符号链接等 reparse point，并在递归复制、恢复或删除前重新扫描目录树，避免词法子路径越界到事务根之外。
- 安装事务启动候选应用时写入带同一 token 的 `active`“验收只读”请求；该阶段发现损坏或不可读主设置时零 prompt、零恢复写入并失败闭锁。`released` 才授权 C# 执行经用户确认的设置恢复和必要的 schema 迁移，C# 写入成功后回报 `ready`，此时窗口仍不可编辑。事务先进入仍可回滚的 `accepted` 并保留备份；写入 `finalized` 后，同一 C# PID 在一个 Dispatcher 回调内启用窗口并原子写出 `finalized-ready` 回执，回执失败会立即重新禁用窗口。安装器持有设置写锁复验回执、会话、进程和任务后才把事务标为 `committed` 并清理证据；此前任一失败都停止候选并回滚。请求 schema 未知、文件缺失、损坏、不可读或 token 变化均保持只读或终止生产启动，失败回滚期间不存在会被旧快照覆盖的新用户保存。
- 启动请求、`window-ready` 与 `finalized-ready` 回执都先写同目录临时文件，再用一次覆盖改名替换目标，读方不会在中间看到文件缺失。对方轮询时用 `File.ReadAllText` 打开的读句柄不共享删除，此刻替换会报 Access denied；安装器侧 `Countdown.Runtime.psm1` 与应用侧 `RuntimeProtocol` 的写方都按设置文件替换的同一预算退避约 2 秒，仍被占用才带路径失败，避免一次轮询撞车让验收失败或让候选应用以未处理异常退出。
- 安装事务的 journal、延期提交回执和 committed 标记也用同样的覆盖改名与退避（`Countdown.InstallTransaction.psm1`），改名失败时旧文件原样保留。不能用 `Move-Item -Force`：它第一次改名失败后会先删除目标再重试，重试仍失败时旧 journal 已经没了，而恢复会跳过没有 `journal.json` 的事务目录。
- `committed` 清理在事务目录外先写 sidecar，再将事务目录同卷原子重命名后删除；即使部分删除已移除内部 journal 或目录重命名失败，后续 recovery 仍能定位并重试，持续失败才报告 unresolved，且 committed 永不重新进入回滚。
- 办公室部署以旧应用停止后的事务快照为基线，在同一设置写锁内比较迁移前后语义并提交事务；任何非允许变化都回滚。

## 启动与发布契约

- `runtime-status.json` 保持 schema v4。
- 回执中的稳定应用身份仍是 `敏敏子倒计时.ps1`，PID 必须对应 `app\MinminCountdown.exe`。
- “启动就绪”仍表示悬浮窗首次完成渲染；节假日日历可以是 `Pending`、`Ready` 或 `Unavailable`。
- 计划任务使用 `pwsh.exe -STA` 启动薄 adapter；这是现役兼容 seam，不表示 C# 应用宿主迁移尚未完成。
- 生产启动回执默认只接受受安装器管理的 C# EXE；旧 PowerShell WPF 宿主仅能在显式兼容回归中启用。
- 安装与办公室部署在提交前重新读取同一 token 的回执，并确认 PID、会话、应用路径仍绑定本次启动；登录任务须回到 `Ready` 且 `lastTaskResult=0`。应用存活由进程路径和 EXE 哈希证明。
- 发布使用 self-contained、single-file、`win-x64`，目标机不需要预装 .NET 10。`Ical.Net 5.2.3`、提醒中心使用的 `CommunityToolkit.Mvvm 8.4.2`、托盘使用的 `H.NotifyIcon.Wpf 2.4.1` 和确认框局部使用的 `WPF-UI 4.3.0` 许可证均为 MIT；WPF-UI 与 H.NotifyIcon 的目标框架资产经 NuGet 官方页面确认与本项目兼容。托盘的传递闭包固定为 `H.NotifyIcon 2.4.1`、`H.GeneratedIcons.System.Drawing 2.4.1` 和 `System.Drawing.Common 10.0.0`，WPF-UI 传递 `WPF-UI.Abstractions 4.3.0`。发布验收必须证明这些依赖进入应用和验证器的 self-contained 依赖闭包，不能依赖目标机 NuGet cache；C# 验证会逐项检查 `app\published-payload.json` 中的四个托盘程序集。版本、传递依赖与随包 notices 见 [第三方依赖许可证清单](第三方依赖许可证.md)，以各项目 `.csproj` 的精确 `PackageReference` 为准。

- 办公室部署只接受干净且与 `origin/main` 相同的 `main`，随后从该提交 clean rebuild C# 产物，再读取清单并打包，避免复用陈旧的忽略目录二进制。
- `Countdown.ReleaseContract.psm1` 是构建、安装、部署和 Core tests 共用的发布契约。`PackageFiles` 只声明办公室安装会加载或安装的文件：部署与安装控制器、安装与远端部署模块、安装事务生命周期 module、adapter、启动器、图标、节假日数据、根目录官方立绘和 `app` 载荷；`IntegrityHashes` 给其中除信任根外的每个文件静态 SHA-256 或载荷清单哈希。C# 源码、测试、构建与验证工具和 `DESIGN.md` 只留在仓库：契约另以 `BuildInputFiles` 声明构建输入（MSBuild 项目闭包，加构建脚本读取的预检模块与许可证原文），正式部署在构建前按提交 blob 身份逐项核对。Install、Deploy 与 contract 自身是明确的 package trust roots，不参与自哈希；远端传输仍由完整 ZIP SHA-256 覆盖。`Countdown.RemoteDeployment.psm1` 属于部署包 implementation，不安装进运行目录；`Countdown.Validation.psm1` 只在本机直接安装时从仓库加载，不进部署包。旧 PowerShell WPF（含它独占的 `Countdown.Core.psm1`）与旧悬浮窗素材只留在仓库作兼容回归夹具，安装事务会从运行目录移除它们的残留，正式 `app` 只保留现役应用资产。

## 日期与下拉控件（#206）

WPF-UI 4.3.0 为原生 WPF 控件提供 [`DefaultDatePickerStyle`](https://github.com/lepoco/wpfui/blob/153baadeaf475875a81a4605881ca5c2dbe53972/src/Wpf.Ui/Controls/DatePicker/DatePicker.xaml) 和 [`DefaultComboBoxStyle`](https://github.com/lepoco/wpfui/blob/153baadeaf475875a81a4605881ca5c2dbe53972/src/Wpf.Ui/Controls/ComboBox/ComboBox.xaml)。这个源码提交由已安装 NuGet 包的 `repository commit` 钉住。项目通过 `WpfUiPickerStyles` 显式继承这些样式，复用库的 `DefaultComboBoxToggleButtonStyle` 模板，沿用 `SelectedDate` / `IsDropDownOpen` 和三个独立时、分、秒下拉；没有改用单值 `TimePicker`，也没有把票据范围改为仅保留原实现。

暖粉模板覆盖几何、颜色和状态：文字区以标准 `ToggleButton` 在释放时打开，箭头保留原有命中区域；日期箭头使用 `Wpf.Ui.Controls.Button`。`WpfUiDatePicker` 只适配项目特有的只读中文日期格式、单份文字留白和 Esc 关闭后的焦点返回。各窗口直接创建该控件，日期/下拉不再需要 Behavior 或 `Attach`。WPF-UI 主题资源只作用于显式 picker 样式，不向应用资源合并全套隐式控件样式。

验证继续通过实际生产控件和既有输入 seam 覆盖文字/箭头打开、键盘、弹层主题、裁切与负例；输入注入器在隔离桌面内激活精确 HWND 的鼠标源，向标准 WPF 处理器提供完整路由事件及线程设备状态，并在手势结束后恢复。`ButtonBase` 自行处理捕获、按下和点击，不注入控件内部状态。旧报告的 `Attached` / `UnattachedNegative` 字段继续保留，分别表示生产适配器与样式接入、同一暖粉模板移除本次文字切换面的负例，不再表示运行时事件挂接；负例仍要求文字不打开、箭头可打开。另补日期变化和弹层关闭后的 `yyyy 年 M 月 d 日` 校验。规则编辑器的各下拉在其实际可见模式下验证。

## 构建与验证

官方六阶段与窗口套件只经根目录 README「本机验证」的低影响启动器运行；CSharp / Ui / SourceValidation 直跑会 fail-closed。命令、隔离默认值和 opt-out 以 README 为准，不在此复制内层命令。

`Countdown.CSharp.Tests.ps1` 覆盖 PowerShell/C# 双向设置兼容、双向 mutex、真实 adapter UI 验证、schema v4 启动回执、EXE PID、真实第二实例和验收只读生命周期。旧 `Countdown.Ui.Tests.ps1` 作为迁移后的兼容回归夹具保留，但生产入口不允许回退到旧 PowerShell WPF，安装目录也不保留该宿主或其素材。

`Countdown.CSharp.Tests.ps1` 以 `MinminCountdown.Verification.exe verify` 跑进程内验证（含桌面工作区），并通过 adapter 的 `--validate-only` report 验收提醒编辑、启动验收、工作日历和报告契约的真实 interface 行为；旧 PowerShell UI 基线中的 DatePicker popup 生命周期以真实 `Popup.Opened` 事件和日历渲染为准，不以最终 `IsOpen` 作为唯一通过条件。

## 候选语言比较

| 方案 | 优点 | 缺点 | 本项目结论 |
| --- | --- | --- | --- |
| C# / .NET WPF | 原生匹配现有 WPF 与 Windows API；静态类型、调试、异步和测试工具成熟；可 self-contained 发布 | 仍是 Windows 专用；需要跟随 .NET LTS 升级并重新发布安全补丁 | 最适合应用宿主 |
| 继续全量 PowerShell | Windows 运维和部署脚本直接；现有知识与模块可复用 | 大型有状态 WPF 宿主的类型、事件和重构反馈弱；维护成本随 UI 复杂度快速上升 | 只保留运维 adapter |
| Python + Qt | 跨平台，业务代码表达简洁，库丰富 | UI 框架和打包模型整体更换；Windows 原生集成、启动体积与签名发布没有迁移收益 | 不推荐 |
| TypeScript + Electron | Web UI 生态成熟，跨平台，界面开发快 | Chromium 体积和更新面大；需重写 WPF 与 Windows 集成；内存占用更高 | 不推荐 |
| Rust | 内存安全、原生性能和单文件部署出色 | Windows 桌面 UI 生态与 WPF 迁移成本高；开发速度和维护门槛不匹配 | 不作为当前全量迁移路线；仅保留为 #189 后置 Tauri 切片闸门候选 |
| C++ | Windows 原生能力和性能上限最高 | 内存安全、构建、依赖和 UI 开发成本显著增加；本项目没有性能压力证明其必要性 | 不推荐 |
| Go | 部署简单、并发和工具链稳定 | 原生桌面 UI 生态弱，WPF 行为需要重做；对当前应用没有明显 leverage | 不推荐 |

## 生命周期

.NET 10 LTS 支持结束不等于应用或 C# 失效。项目需要在支持期内升级到后续受支持的 .NET 版本、重新运行回归并发布新的 self-contained EXE。self-contained 只消除目标机预装运行时的要求，不会自动获得运行时安全更新。
