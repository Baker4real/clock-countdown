# 设置与持久化

`settings.json` 是设备本地用户状态，保存倒计时、便签和显示/工资偏好。它不得提交；部署也不会以另一台设备的状态覆盖它。

## 规范格式

应用只写入 schema v10，且固定使用 `China Standard Time`。规范格式包含：

- `displayPrecision`、`monthlySalary`、`workStart`、`workEnd`：应用级偏好；上下班时间为 `HH:mm`。
- `themePreference`：主题偏好，只能是 `Auto`、`Day` 或 `Night`。`Auto` 按北京时间 07:00（含）至 19:00（不含）自动选择日间，其余时间为夜间；`Day` / `Night` 手动覆盖时间。
- `tags`：共享标签库。每项都有唯一 ID、非空且大小写不重复的名称，以及可选的 `color`。颜色只辅助显示，关联和筛选始终以 ID 为准。
- `countdowns`：每项都有唯一 ID、大小写不重复的名称、UTC 截止时刻、去重的 `tagIds` 数组，以及 0 至 8 条 `reminderRules`。
- `notes`：每项都有唯一 ID、非空且不超过 140 个字符的正文、`date`、布尔值 `isCompleted`、去重的 `tagIds` 数组，以及 0 至 8 条 `reminderRules`。`date` 只能是严格的 `yyyy-MM-dd`，历史便签无法推断日期时为 `null`；新建或编辑便签必须选择日期。数组位置保留添加顺序，编辑和完成状态变更不移动记录；完整管理窗口据此在同一日期内显示较新添加项。
- `reminderRules`：每条规则都有全局唯一且稳定的非空 `id`。两类记录都接受 `{ id, type: "absoluteOnce", scheduledUtc }`、`{ id, type: "fixedInterval", firstDueUtc, intervalMinutes }` 和类型化 `calendar`；用户倒计时还接受 `{ id, type: "countdownRelative", offsetMinutesBefore }`。`calendar` 共同字段为 `frequency`、1 至 999 的整数 `interval`、`yyyy-MM-dd` 的 `startDate` 与 `HH:mm` 的 `localTime`；`daily` 无额外字段，`weekly` 需要非空且不重复的 `weekdays`，`monthly` 必须且只能有 1 至 31 的 `day` 或 `lastDay: true`，`yearly` 还需 1 至 12 的 `month` 并同样二选一。星期按周一至周日规范排序。自由格式 RRULE、例外日期、次数、截止日期、未知频率及外来字段全部拒绝。所有绝对时间和发生项规范为 UTC；calendar 输入按 `China Standard Time` 解释，不存在日期跳过而不夹取，显式最后一天按实际月长计算。固定间隔为 1 至 1440 整数分钟，相对偏移为 0 至 5,256,000 整数分钟；相对 occurrence 实时等于倒计时 `targetUtc - offsetMinutesBefore`，文件中不缓存派生 UTC。同一记录不得包含重复的规范日程，各分支不得携带其他分支字段。
- 便签规则编辑以完整规则集合为草稿；正文、日期、标签和规则集合在一次 `SaveNoteChange` 中提交。写盘成功后才替换内存并同步 scheduler/提醒中心；失败时磁盘、工作区快照、调用方规则数组和可见中心条目均保持原状态。删除或改变规则只清理不再存在或日程已改变的 rule state，不清理同便签其他稳定规则的 cursor。
- `reminderStates`：顶层按 rule ID 索引的有界状态对象。状态只含可空的 `handledThroughUtc`、`lastDeliveredOccurrenceKey`、`lastDispositionOccurrenceKey` 与 `activeSnooze`；四者不能同时为空。送达和处置 key 必须属于对应规则、使用规范 UTC occurrence、落在 cursor 之内；处置还必须具有送达事实且不能晚于最后送达。`activeSnooze` 必须绑定最后送达且尚未处置的同一 occurrence，并包含一致的 `occurrenceKey`、`originalScheduledUtc` 和更晚的 `snoozeUntilUtc`。读取器兼容此前 provisional `lastAcknowledgedOccurrenceKey` 输入，规范写出只使用 `lastDispositionOccurrenceKey` 并显式写出可空 `activeSnooze`；没有状态的规则保持未处理。

occurrence key 固定为 `<ruleId>|<scheduledUtc:o>`，其中时间先规范为 UTC。读取、迁移失败重试和 canonical 往返不会重建 rule ID 或改变 occurrence key。calendar cursor 和 occurrence 还必须落在按北京时间计算出的真实类型化日程上；冷启动或调度延迟只处理 cursor 之后最新的一个错过 occurrence。每个 `tagIds` 都必须引用 `tags` 中存在的标签。读取规范 schema v10 时会校验这些约束及主题偏好；未知规则、重复规则或日程、超过 8 条、全局重复 ID、悬空或空状态、过早 cursor、互相矛盾的 occurrence/cursor/delivery/disposition/snooze，以及其他无效或缺失字段都会直接报错，不会静默修正。

## 启动迁移

普通交互模式在任何设置读取、恢复判断或迁移写回之前，先取得按当前 Windows 用户、应用根和规范设置路径作用域化的单实例租约，并为主实例建立同 scope 的命名管道监听器。第二实例不读取、恢复或迁移设置，只发送一次有界激活请求；只有协议版本、scope identity、request identity 和成功结果全部匹配的 ACK 才返回成功。超时、协议不匹配、断连或监听失败都返回失败并写入不含设置内容的诊断事件。

激活处理只调用现役悬浮窗/托盘生命周期入口，不进入 `DesktopWorkspace` 候选提交。因此它不写 `settings.json` 或备份，不改变当前工作区、标签/状态筛选、正文搜索、日期筛选或编辑草稿，也不显示或重置管理窗口。`-ValidateOnly`、exercise 探针和 acceptance-read-only 安装/部署验收不发送交互激活请求，也不把 ACK 当作验证成功条件。

普通启动可读取历史格式，并在非 `-ValidateOnly` 模式下写回规范的 schema v10。schema v1-v8 都没有主题偏好，迁移时统一补为 `Auto`：

- schema v1 的单个截止时间迁移为“我的倒计时”，使用默认偏好、空便签和空标签库。
- schema v2 的倒计时保留，使用默认偏好、空便签和空标签库。
- schema v3 的倒计时与偏好保留，并新增空便签列表、空标签库和各记录的空 `tagIds`。
- schema v4 保留有效的 `notes` 列表，并新增空标签库、各倒计时和便签的空 `tagIds`，以及便签的 `date: null`。
- schema v5 保留有效的标签库及 `tagIds` 关联，并为每条既有便签新增 `date: null`。
- schema v6 必须已经包含有效的 `tags`、`tagIds` 和便签 `date` 字段；日期值只能为 `null` 或严格的 `yyyy-MM-dd`。
- schema v6 及更早版本的既有便签迁移为空 `reminderRules`，不会擅自开启提醒。
- schema v7 必须包含合法且成对出现的旧提醒字段；关闭提醒迁移为空规则，循环提醒迁移为 `fixedInterval`，`firstDueUtc` 等于旧 `reminderStartUtc` 加一个间隔。
- schema v8 必须包含合法且分支严格的旧 `reminder` 对象。
- schema v9 在保留 schema v8 的标签、日期和提醒约束上，必须额外包含合法的 `themePreference`；随后与 v8 一同进入 v10 规则迁移。

旧 `none` 迁移为 0 条规则；pending `once` 迁移为无状态的 `absoluteOnce`；delivered `once` 迁移时同时写入计划时刻 cursor 和对应 occurrence key，因此升级后不会复活。旧 `repeat` 迁移为 `fixedInterval`；若迁移时已经开始，只把 cursor 推进到不晚于注入迁移时钟的最新周期，不逐个补发此前周期，也不声称这些周期已经渲染送达。迁移 rule ID 由来源类型、记录 ID 和旧提醒分支经 SHA-256 稳定派生，不使用随机 ID；同一输入在重复读取或迁移失败重试后得到相同 ID。

`-ValidateOnly` 保持传入的设置文件只读，不会执行迁移写回。

## 写入与界面提交

倒计时、主题偏好、其他偏好、便签和标签操作先构造完整候选状态，再校验并在按设置路径命名的跨进程写锁内写入同目录的 `.tmp` 文件。已有主文件必须先通过同一严格读取合同；随后只把合法的旧 backup 1 原子轮转到 `settings.json.backup2`，再由一次 `File.Replace` 同时提交候选主文件并把旧主文件保存为 `settings.json.backup1`。无效主文件绝不晋升；backup 轮转或主替换失败会还原已经轮转的 backup 2，主文件与界面候选都不提交。若 backup 2 的回滚本身失败，原 backup 2 的唯一字节保留在 `settings.json.backup2.rollback`，后续保存会失败闭锁，不得覆盖该未决 artifact。所有设置和备份写出均为 UTF-8 无 BOM。

成功替换 `settings.json` 后才提交到界面内存状态。主题按钮每次点击先按“自动→日间→夜间→自动”生成候选偏好，只有写盘成功后才更新按钮和两个窗口的生效主题。办公室部署的最终设置读取、等价验证和事务提交持有同一把锁，因此应用保存要么先完成并进入验收，要么等部署提交后继续。写入失败会向用户显示错误，原有记录、偏好、标签库、筛选状态和编辑草稿保持不变。便签编辑先由 `ReminderEditing` 生成并校验领域提醒，再以 `SaveNoteChange` 交给 `DesktopWorkspace.Apply`；保存、完成状态和删除最终都由 `ApplicationSession.TryCommit` 进入同一持久化契约。旧 `Invoke-NoteMutation` 只属于 PowerShell 兼容回归夹具，不是生产写入路径。

标签删除也是同一候选事务：它只会从倒计时和便签的 `tagIds` 中解除该标签，不会删除或改写记录本身。标签改名会保留其 ID，因此已有关联无需迁移。

用户倒计时的名称、目标、标签和完整规则集合在一次 `SaveCountdownChange` 中提交。新建相对规则或修改目标后，所有相对派生时刻必须仍晚于提交时的真实时钟；任一失败时目标、规则、内存、磁盘、cursor 和提醒中心均保持原样。目标变化保留 rule ID，未送达 occurrence 随新目标重算；已经确认送达的历史相对 occurrence 继续允许知道了或稍后处置。删除规则或整个倒计时在同一事务清除对应 `reminderStates`，协调器在同一 tick 移除现役中心条目。

主窗口与悬浮窗现役便签入口共用 0 至 8 条规则编辑器，支持新增、原位编辑、复制和删除 `absoluteOnce` / `fixedInterval` / `calendar` 规则；原位编辑保留既有 rule ID，新建或复制生成新 ID。旧“不提醒 / 仅一次 / 重复提醒”三模式只保留为兼容 adapter，用于旧调用方和回归夹具，不是现役多规则 UI。提醒时间由用户按北京时间选择，保存为规范 UTC；新增或改期规则在最终便签事务提交前再次按实时 clock 校验，窗口停留期间已经过期时会保留草稿并把错误归位到首次提醒字段，未改日程的历史规则与规则删除不受该未来时间门槛影响。一次规则到期后若应用未运行，会在下次启动立即补发。宿主在应用运行期间只维护一个提醒中心；同一 tick 的发生项批量加入，后续到期项追加到现有中心，并按计划 UTC、稳定记录顺序和规则顺序排列。每条规则最多保留一个未解决 occurrence；送达失败或活动稍后期间不展示同规则的新基础周期，处置后只选择 cursor 之后的最新周期。每个条目独立通过真实 WPF loaded/render probe 后才确认对应 occurrence；仅调用 `Show()` 不推进 `reminderStates`。送达状态写盘失败时，磁盘设置、界面内存和 cursor 都保持不变，对应条目显示失败状态，禁用“知道了 / 稍后提醒 / 完成便签”，保留“打开来源”，并按 5、10、20 秒及最高 30 秒间隔无限重试；成功后才推进 cursor 并保存最后送达 key。

“知道了”是独立的持久化动作：成功写入 `lastDispositionOccurrenceKey` 后才移除当前条目，不禁用基础重复规则；失败时条目保留、按钮禁用并按同一退避节奏自动重试。稍后提醒可选相对成功操作时刻的 10、30、60 分钟、下一个北京时间日历日 09:00，或自定义未来北京时间；无效自定义值只在来源控件旁显示错误，不改变状态。成功稍后只在 `activeSnooze` 保存同一 occurrence key、原计划 UTC 与覆盖 UTC，移除当前条目但不改写基础规则，跨重启到覆盖时刻仍恢复同一 occurrence。最后一项移除后中心关闭，之后的新 occurrence 仍能重新打开中心。

“完成便签”在一个候选事务中标记便签完成、推进各规则 cursor、处置已送达 occurrence 并清除活动稍后项；成功后才移除该便签的中心条目，失败时设置、内存和条目全部保持原样并自动重试。重新打开便签时再次推进规则到提交时刻，之后只恢复严格未来的 occurrence；未来尚未到期的绝对规则不被误吞。“打开来源”会恢复已最小化的管理窗口并揭示、聚焦准确便签或倒计时编辑表单，不改变 occurrence 的送达或处置状态，也不清空既有筛选和编辑草稿；绕过便签筛选只作用于本次定位渲染，后续刷新重新服从原筛选。大量条目和长正文只在中心的单一滚动列表中扩展；倒计时项只提供“知道了 / 稍后提醒 / 打开来源”，便签项额外提供“完成便签”，均不提供删除。送达合同见 [#13](https://github.com/Baker4real/clock-countdown/issues/13)，v10 规则与 cursor 合同见 [#14](https://github.com/Baker4real/clock-countdown/issues/14)，提醒中心合同见 [#15](https://github.com/Baker4real/clock-countdown/issues/15)，持久化处置、稍后提醒与完成动作见 [#17](https://github.com/Baker4real/clock-countdown/issues/17)，倒计时相对规则与统一来源见 [#18](https://github.com/Baker4real/clock-countdown/issues/18)。提醒由正在运行的应用负责，不是 Windows 系统级通知服务。

## 启动恢复

- 只有设置路径真正不存在时才按合法首次运行处理，不读取备份，也不提示恢复。目录、reparse point 或其他非普通对象占用该路径时失败闭锁；状态探测 access denied 也必须传播失败，不能退化为空设置。
- 任何可读且严格合法的主文件始终优先，包括空集合或记录数少于备份；不会用数量、时间戳或备份内容猜测用户意图。
- 主文件存在但不可读或严格校验失败时，分别验证 backup 1 和 backup 2，只提供代次最新的合法候选。用户必须明确选择“恢复备份”或“退出”；没有静默恢复，也没有“以空设置继续”。
- 用户批准后，若损坏主文件字节可读，先在设置同目录的 `settings-recovery-evidence` 中写入带 UTC 时间戳和唯一后缀的逐字节原始证据。候选以 canonical schema v10、UTF-8 无 BOM 写入同目录临时文件，再原子替换主路径。
- 替换时由系统同时保留 rollback 文件；恢复后从主路径重新读取并执行同一严格校验。回读失败会先还原原主文件再退出；原文件无法还原时也不会启动交互宿主。即使损坏主文件因读取失败而无法另写 evidence，回滚失败时仍保留包含原主逐字节内容的 recovery rollback artifact，不会在 `finally` 中删除唯一恢复来源。
- `settings.json.backup1`、`settings.json.backup2`、`settings-recovery-evidence` 和恢复临时/rollback 文件都是设备本地状态，不属于 release contract、诊断正文或跨设备部署输入；部署仍不得用另一台设备的这些文件覆盖目标机。

## 诊断日志

普通运行会在应用目录的 `logs\application.jsonl` 写入逐行 JSON 诊断事件，覆盖进程启动、正常退出、窗口首次渲染、单实例激活结果、节假日日历状态和致命未捕获异常。激活事件只保存散列 scope identity、随机 request identity、结果、前后窗口状态、管理窗口可见性和交互悬浮窗数量。单个日志达到 1 MiB 前会滚动，最多保留 `.1`、`.2`、`.3` 三份历史文件；日志写入失败不会覆盖原始应用异常。

日志不写入便签正文、标签名称、工资、设置 JSON、设置备份、恢复证据或设备凭据。恢复路径只记录不含异常正文的状态事件名。致命异常只保留异常类型、系统异常消息、`HResult` 和截断后的 .NET 堆栈。`-ValidateOnly` 默认不落日志，只有测试显式传入 `-DiagnosticLogPath` 时才启用。

## 办公室部署边界

部署允许 `settings.json` 完全不变；若文件发生变化，只允许严格等价的 schema v3-v9 到 v10 迁移。v3-v6 按上述规则补齐字段并保持提醒关闭；v7 的循环提醒必须保持相同首次到期时间和间隔；v8-v9 的旧提醒语义、标签、日期和主题偏好必须等价迁移为规则与有界状态。schema v3-v8 只能补入 `themePreference: "Auto"`，不得伪造手动日间或夜间；schema v9 必须保留已有主题偏好。时区、其他偏好、标签关联、记录顺序、UTC 值以及每个既有倒计时和便签的领域值必须等价。任何其他变化都会使部署验收失败并触发回滚。详细流程见 [办公室部署](办公室部署.md)。
