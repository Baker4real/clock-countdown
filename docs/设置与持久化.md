# 设置与持久化

`settings.json` 是设备本地用户状态，保存倒计时、便签和显示/工资偏好。它不得提交；部署也不会以另一台设备的状态覆盖它。

## 规范格式

应用只写入 schema v9，且固定使用 `China Standard Time`。规范格式包含：

- `displayPrecision`、`monthlySalary`、`workStart`、`workEnd`：应用级偏好；上下班时间为 `HH:mm`。
- `themePreference`：主题偏好，只能是 `Auto`、`Day` 或 `Night`。`Auto` 按北京时间 07:00（含）至 19:00（不含）自动选择日间，其余时间为夜间；`Day` / `Night` 手动覆盖时间。
- `tags`：共享标签库。每项都有唯一 ID、非空且大小写不重复的名称，以及可选的 `color`。颜色只辅助显示，关联和筛选始终以 ID 为准。
- `countdowns`：每项都有唯一 ID、大小写不重复的名称、UTC 截止时刻，以及去重的 `tagIds` 数组。
- `notes`：每项都有唯一 ID、非空且不超过 140 个字符的正文、`date`、布尔值 `isCompleted`、去重的 `tagIds` 数组，以及判别对象 `reminder`。`date` 只能是严格的 `yyyy-MM-dd`，历史便签无法推断日期时为 `null`；新建或编辑便签必须选择日期。数组位置保留添加顺序，编辑和完成状态变更不移动记录；完整管理窗口据此在同一日期内显示较新添加项。提醒对象只能是 `{ "type": "none" }`、包含 `firstDueUtc` 与 `delivery: "pending" | "delivered"` 的 `once`，或包含 `firstDueUtc` 与 1 到 1440 整数分钟 `intervalMinutes` 的 `repeat`。各分支不得携带其他分支的字段。

每个 `tagIds` 都必须引用 `tags` 中存在的标签。读取规范 schema v9 时会校验这些约束及主题偏好；无效、重复、悬空或缺失字段会直接报错，不会静默修正。

## 启动迁移

普通启动可读取历史格式，并在非 `-ValidateOnly` 模式下写回规范的 schema v9。schema v1-v8 都没有主题偏好，迁移时统一补为 `Auto`：

- schema v1 的单个截止时间迁移为“我的倒计时”，使用默认偏好、空便签和空标签库。
- schema v2 的倒计时保留，使用默认偏好、空便签和空标签库。
- schema v3 的倒计时与偏好保留，并新增空便签列表、空标签库和各记录的空 `tagIds`。
- schema v4 保留有效的 `notes` 列表，并新增空标签库、各倒计时和便签的空 `tagIds`，以及便签的 `date: null`。
- schema v5 保留有效的标签库及 `tagIds` 关联，并为每条既有便签新增 `date: null`。
- schema v6 必须已经包含有效的 `tags`、`tagIds` 和便签 `date` 字段；日期值只能为 `null` 或严格的 `yyyy-MM-dd`。
- schema v6 及更早版本的既有便签迁移为 `none`，不会擅自开启提醒。
- schema v7 必须包含合法且成对出现的旧提醒字段；关闭提醒迁移为 `none`，循环提醒迁移为 `repeat`，`firstDueUtc` 等于旧 `reminderStartUtc` 加一个间隔。
- schema v8 必须包含合法且分支严格的 `reminder` 对象。
- schema v9 在保留 schema v8 的标签、日期和提醒约束上，必须额外包含合法的 `themePreference`。

`-ValidateOnly` 保持传入的设置文件只读，不会执行迁移写回。

## 写入与界面提交

倒计时、主题偏好、其他偏好、便签和标签操作先构造完整候选状态，再校验并在按设置路径命名的跨进程写锁内写入同目录的 `.tmp` 文件；成功替换 `settings.json` 后才提交到界面内存状态。主题按钮每次点击先按“自动→日间→夜间→自动”生成候选偏好，只有写盘成功后才更新按钮和两个窗口的生效主题。办公室部署的最终设置读取、等价验证和事务提交持有同一把锁，因此应用保存要么先完成并进入验收，要么等部署提交后继续。写入失败会向用户显示错误，原有记录、偏好、标签库、筛选状态和编辑草稿保持不变。便签编辑先由 `ReminderEditing` 生成并校验领域提醒，再以 `SaveNoteChange` 交给 `DesktopWorkspace.Apply`；保存、完成状态和删除最终都由 `ApplicationSession.TryCommit` 进入同一持久化契约。旧 `Invoke-NoteMutation` 只属于 PowerShell 兼容回归夹具，不是生产写入路径。

标签删除也是同一候选事务：它只会从倒计时和便签的 `tagIds` 中解除该标签，不会删除或改写记录本身。标签改名会保留其 ID，因此已有关联无需迁移。

提醒时间由用户按北京时间选择，保存为 UTC `firstDueUtc`。`once` 到期后若应用未运行，会在下次启动立即补发。当前宿主在 `ReminderWindow.Show()` 返回后调用送达确认，不等待 `ContentRendered`；若随后持久化 `delivery: "delivered"` 失败，磁盘上的设置仍为 `pending`，但当前进程的调度器锁存已经更新，因此不会在同一进程内重试。现状不能表述为已具备基于真实渲染确认的 at-least-once 保证；该修复仍属于待实现的 [#13](https://github.com/Baker4real/clock-countdown/issues/13)。`repeat` 从首次到期时间按整数分钟循环，单次运行内每个周期只弹一次；重启或恢复未完成状态时从当前周期继续，不逐个补发停机或完成期间错过的周期。便签标记完成、切换为 `none` 或删除后不再弹出。提醒由正在运行的应用负责，不是 Windows 系统级通知服务。

## 诊断日志

普通运行会在应用目录的 `logs\application.jsonl` 写入逐行 JSON 诊断事件，覆盖进程启动、正常退出、窗口首次渲染、节假日日历状态和致命未捕获异常。单个日志达到 1 MiB 前会滚动，最多保留 `.1`、`.2`、`.3` 三份历史文件；日志写入失败不会覆盖原始应用异常。

日志不写入便签正文、标签名称、工资、设置 JSON 或设备凭据。致命异常只保留异常类型、系统异常消息、`HResult` 和截断后的 .NET 堆栈。`-ValidateOnly` 默认不落日志，只有测试显式传入 `-DiagnosticLogPath` 时才启用。

## 办公室部署边界

部署允许 `settings.json` 完全不变；若文件发生变化，只允许严格等价的 schema v3-v8 到 v9 迁移。v3-v6 按上述规则补齐字段并保持提醒关闭；v7 的循环提醒必须保持相同首次到期时间和间隔；v8 的标签、日期和提醒对象原样保留。所有历史版本只能补入 `themePreference: "Auto"`，不得伪造手动日间或夜间。时区、其他偏好、标签关联以及每个既有倒计时和便签的领域值必须等价。任何其他变化都会使部署验收失败并触发回滚。详细流程见 [办公室部署](办公室部署.md)。
