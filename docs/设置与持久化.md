# 设置与持久化

`settings.json` 是设备本地用户状态，保存倒计时、便签和显示/工资偏好。它不得提交；部署也不会以另一台设备的状态覆盖它。

## 规范格式

应用只写入 schema v6，且固定使用 `China Standard Time`。规范格式包含：

- `displayPrecision`、`monthlySalary`、`workStart`、`workEnd`：应用级偏好；上下班时间为 `HH:mm`。
- `tags`：共享标签库。每项都有唯一 ID、非空且大小写不重复的名称，以及可选的 `color`。颜色只辅助显示，关联和筛选始终以 ID 为准。
- `countdowns`：每项都有唯一 ID、大小写不重复的名称、UTC 截止时刻，以及去重的 `tagIds` 数组。
- `notes`：每项都有唯一 ID、非空且不超过 140 个字符的正文、`date`、布尔值 `isCompleted`，以及去重的 `tagIds` 数组。`date` 只能是严格的 `yyyy-MM-dd`，历史便签无法推断日期时为 `null`；新建或编辑便签必须选择日期。

每个 `tagIds` 都必须引用 `tags` 中存在的标签。读取规范 schema v6 时会校验这些约束；无效、重复、悬空或缺失字段会直接报错，不会静默修正。

## 启动迁移

普通启动可读取历史格式，并在非 `-ValidateOnly` 模式下写回规范的 schema v6：

- schema v1 的单个截止时间迁移为“我的倒计时”，使用默认偏好、空便签和空标签库。
- schema v2 的倒计时保留，使用默认偏好、空便签和空标签库。
- schema v3 的倒计时与偏好保留，并新增空便签列表、空标签库和各记录的空 `tagIds`。
- schema v4 保留有效的 `notes` 列表，并新增空标签库、各倒计时和便签的空 `tagIds`，以及便签的 `date: null`。
- schema v5 保留有效的标签库及 `tagIds` 关联，并为每条既有便签新增 `date: null`。
- schema v6 必须已经包含有效的 `tags`、`tagIds` 和便签 `date` 字段；日期值只能为 `null` 或严格的 `yyyy-MM-dd`。

`-ValidateOnly` 保持传入的设置文件只读，不会执行迁移写回。

## 写入与界面提交

倒计时、偏好、便签和标签操作先构造完整候选状态，再校验并写入同目录的 `.tmp` 文件，成功替换 `settings.json` 后才提交到界面内存状态。写入失败会向用户显示错误，原有记录、标签库、筛选状态和编辑草稿保持不变。便签操作通过 `Invoke-NoteMutation` 遵循同一契约；没有实际变更的操作不会写盘。

标签删除也是同一候选事务：它只会从倒计时和便签的 `tagIds` 中解除该标签，不会删除或改写记录本身。标签改名会保留其 ID，因此已有关联无需迁移。

## 诊断日志

普通运行会在应用目录的 `logs\application.jsonl` 写入逐行 JSON 诊断事件，覆盖进程启动、正常退出、窗口首次渲染、节假日日历状态和致命未捕获异常。单个日志达到 1 MiB 前会滚动，最多保留 `.1`、`.2`、`.3` 三份历史文件；日志写入失败不会覆盖原始应用异常。

日志不写入便签正文、标签名称、工资、设置 JSON 或设备凭据。致命异常只保留异常类型、系统异常消息、`HResult` 和 PowerShell 脚本堆栈。`-ValidateOnly` 默认不落日志，只有测试显式传入 `-DiagnosticLogPath` 时才启用。

## 办公室部署边界

部署允许 `settings.json` 完全不变；若文件发生变化，只允许严格等价的 schema v3、v4 或 v5 到 v6 迁移：v3 的便签必须保持为空；v4 的便签必须逐项保持等价，只能新增空的 `tags`、空的 `tagIds` 和 `date: null`；v5 必须保留标签关联并且只能为既有便签新增 `date: null`。时区、偏好以及每个既有倒计时的 ID、名称和 UTC 时刻必须等价。任何其他变化都会使部署验收失败并触发回滚。详细流程见 [办公室部署](办公室部署.md)。
